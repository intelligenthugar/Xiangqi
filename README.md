# 象棋網站（Xiangqi）

> 專案類型：靜態網站／瀏覽器象棋遊戲\
> 部署方式：GitHub Pages\
> 目前文件對應版本：**v46**

本文件介紹網站的主要功能、檔案結構、運作方式、部署流程、Firebase
設定注意事項，以及版本更新紀錄。由於早期版本的逐次變更紀錄並未完整保留，早期版本以版本區間整理；有明確記錄的近期版本則逐版列出，避免把未確認的修改當成事實。

## 1. 功能介紹

### 1.1 首頁

-   提供網站入口與主要功能導覽。
-   可進入單機對戰、連線對戰及積分排位賽。
-   支援深色介面與行動裝置版面。
-   部分玩家狀態與網站資訊會透過 Firebase 讀取。

### 1.2 單機對戰

-   可在同一台裝置上與 AI 對弈。
-   提供不同 AI 難度（實際選項依目前程式設定為準）。
-   可重新開始棋局。
-   **按下「重來」會先顯示確認提示**；取消即可保留原本棋局，確認後才重置。

### 1.3 連線對戰

-   提供線上房間／連線對戰相關功能。
-   房間及對局資料透過 Firebase Realtime Database 同步。
-   連線功能需要正確設定 Firebase
    專案、驗證方式與資料庫規則；若設定不正確，可能無法建立房間或同步棋步。

### 1.4 積分排位賽

-   排位賽使用固定難度，避免玩家自行選擇不同難度造成不公平。
-   顯示玩家積分與排行榜；排行榜介面以目前程式實作為準，設計目標為顯示前
    10 名。
-   登入並具備有效玩家資料後，才能保存個人排位紀錄。
-   進入排位賽時，程式應先等待 Firebase
    還原登入狀態，再判斷是否需要顯示登入視窗。
-   登入與註冊視窗應避免重複開啟；登入只需要電子郵件與密碼，使用者名稱在註冊時填寫。
-   **按下「重來」會先跳出確認提示。** 若排位賽已超過 5
    步，確認重來會依遊戲規則判定該局認輸；5
    步以內則可確認後重新開始。請以實際部署版本的程式邏輯為準。

> 注意：前端鎖定模式或難度，不等於具備完整的伺服器端防作弊。若積分寫入權限允許使用者直接修改自己的分數，仍可能被惡意竄改。正式競技環境應把結果驗證與積分計算移至可信任的伺服器端。

### 1.5 帳號系統

-   使用 Firebase Authentication 的電子郵件／密碼登入方式。
-   註冊時填寫電子郵件、密碼及使用者名稱。
-   登入時只需填電子郵件與密碼。
-   帳號登入狀態會由 Firebase 的登入狀態監聽器恢復及更新。
-   玩家資料與對戰紀錄依程式設計儲存在 Firebase Realtime Database。

### 1.6 管理員頁面

-   專案含有 `admin.html` 管理頁面。
-   管理功能會依程式設定的管理員 UID 判斷權限。
-   管理頁面顯示的在線資訊與管理項目，以目前版本的程式及 Firebase
    規則為準。
-   不要只依靠前端隱藏按鈕保護管理功能；資料庫規則也必須驗證權限。

### 各檔案用途

  檔案                                用途

                                      覆蓋

> 設定。請務必保留該檔案。

## 3. 網站如何運作

### 3.1 靜態網頁與 GitHub Pages

網站的 HTML、CSS 及 JavaScript 由瀏覽器載入。GitHub Pages
負責提供靜態檔案，不會自動執行伺服器端程式。

因此： - 一般介面、棋盤繪製及部分遊戲邏輯在使用者的瀏覽器執行。 - AI
的前端計算會使用玩家裝置的 CPU。 -
連線房間、帳號、玩家資料及排行榜等雲端功能，需依賴 Firebase。 - 若
JavaScript 發生語法錯誤，相關程式可能無法啟動，導致棋盤空白或按鈕失效。

### 3.2 Firebase Authentication

登入流程通常如下：

1.  網頁載入 Firebase SDK 與專案設定。
2.  Firebase 嘗試還原先前的登入狀態。
3.  `onAuthStateChanged` 回報已登入的使用者，或確認目前沒有登入使用者。
4.  網站依登入狀態決定是否顯示登入視窗。
5.  登入成功後，再讀取玩家名稱、積分及其他帳號資料。

**重要：不能在 Firebase 尚未確認登入狀態時，就直接把
`currentUser === null` 當成未登入。**
網路延遲或初始化順序可能造成登入視窗重複跳出。應共用登入狀態初始化流程，並為登入視窗加上防重複機制。

### 3.3 Firebase Realtime Database

資料庫用於保存需要跨裝置同步的資料，例如房間、玩家資料、對戰紀錄及排行榜。實際路徑與資料欄位由
`js/chess.js`、`js/home.js` 及 Firebase Database Rules 共同決定。

資料庫規則至少應遵守： - 一般使用者只能讀寫自己有權存取的資料。 -
管理員操作必須在資料庫規則中驗證管理員權限。 -
不應因為前端隱藏功能，就假設資料已受到保護。 -
不要將密碼或服務帳號私鑰寫進前端程式。Firebase 網頁設定中的 API key
並非伺服器私鑰，但仍須搭配正確的 Authentication 與 Database Rules。

### 3.4 排位積分與公平性

前端可負責顯示積分、限制選單及呈現比賽結果，但前端程式可被使用者檢視或修改。若需要可信任的競技排名，應由後端驗證棋步、結果與積分變化，再寫入排行榜。只靠瀏覽器端的判定無法完全防止作弊。

## 4. GitHub Pages 部署與更新

1.  下載專案 ZIP。
2.  解壓縮，確認檔案結構正確。
3.  將更新檔案上傳至 GitHub 儲存庫的對應路徑。
4.  覆蓋同名的 HTML、CSS、JavaScript 檔案。
5.  **保留原本的 `js/firebase-config.js`，不要刪除或覆蓋。**
6.  在 GitHub Pages 設定中確認發布分支及資料夾正確。
7.  等待 GitHub Pages 部署完成。
8.  開啟網站並使用 `Ctrl + F5` 強制重新整理，排除舊快取影響。

### 更新後的檢查清單

-   [ ] 首頁能正常顯示。
-   [ ] 棋盤能正常載入，沒有 JavaScript SyntaxError。
-   [ ] 單機對戰可以走棋，AI 能回應。
-   [ ] 重來按鈕會先顯示確認提示。
-   [ ] 排位賽使用固定難度。
-   [ ] 排位賽超過 5 步後，確認重來會依規則判負。
-   [ ] 已登入使用者進入排位賽時不會重複跳出登入視窗。
-   [ ] 積分及排行榜能正確讀取。
-   [ ] 連線房間可以建立、加入及同步棋步。
-   [ ] 手機版排版正常。
-   [ ] 管理員頁面權限符合預期。

## 5. 常見問題排查

### 棋盤空白

1.  開啟瀏覽器開發者工具（Windows 通常按 `F12`）。
2.  切到 **Console**。
3.  找第一個紅色錯誤，而不是只看最後一個訊息。
4.  記錄錯誤檔案、行號及版本參數。
5.  確認 GitHub 上的檔案已更新，並按 `Ctrl + F5`。
6.  檢查 JavaScript 語法及 Firebase SDK 是否成功載入。

`favicon.ico 404`
通常只表示網站圖示不存在，與棋盤程式的語法錯誤通常無直接關係。

### 登入視窗重複出現

-   確認所有頁面載入的是預期版本的 `js/chess.js` 與 `js/home.js`。
-   確認登入狀態只由共用的 Firebase Auth 狀態流程判定。
-   確認 Firebase 尚未完成狀態恢復時，程式不會立刻開啟登入視窗。
-   確認多個初始化函式共用同一個 Promise 或狀態鎖。
-   確認登入視窗已開啟時，不會再次建立另一個視窗。

### 積分沒有更新

-   確認 Firebase Authentication 顯示目前帳號已登入。
-   確認玩家 UID 與資料庫玩家資料路徑一致。
-   確認資料庫讀取權限正確。
-   區分「尚在載入」、「沒有資料」及「讀取失敗」，不要全部顯示成未登入。

### 連線對戰無法使用

-   確認 Firebase 設定檔仍存在且內容正確。
-   確認 Realtime Database 已建立。
-   檢查 Database Rules 是否允許必要的讀寫操作。
-   查看 Console 與 Network 錯誤，不要為了方便而把資料庫規則全部開放。

-   每次更新後，記錄版本號、修改日期、修改檔案、修正內容及測試結果。
-   重大功能修改前，先保留上一個可正常運作的版本。
