# 象棋網站（Xiangqi）

> 專案類型：靜態網站／瀏覽器象棋遊戲
> 部署方式：GitHub Pages
> 目前文件對應版本：**v48**

本文件介紹網站的主要功能、AI 與排位系統、檔案結構、運作方式、部署流程、Firebase 設定注意事項，以及版本更新紀錄。
早期版本的逐次變更紀錄並未完整保留，早期版本以版本區間整理；有明確記錄的近期版本則逐版列出，避免把未確認的修改當成事實。

## 1. 功能介紹

### 1.1 首頁

- 提供網站入口與主要功能導覽。
- 可進入單機對戰、連線對戰及積分排位賽。
- 支援深色介面與行動裝置版面。
- 部分玩家狀態與網站資訊會透過 Firebase 讀取。

### 1.2 單機對戰

- 可與 AI 對弈，玩家固定執紅，AI 執黑。
- AI 提供兩種難度：

  | 難度 | 說明 |
  |---|---|
  | **新手** | 看 2 步，偶爾會亂走，適合練習 |
  | **大師** | 完整強度，每步思考約 1.5 秒 |

- 可重新開始棋局。
- **按下「重來」會先顯示確認提示**；取消即可保留原本棋局，確認後才重置。

### 1.3 連線對戰

- 提供線上房間／連線對戰相關功能。
- 房間及對局資料透過 Firebase Realtime Database 同步。
- 連線功能需要正確設定 Firebase 專案、驗證方式與資料庫規則；若設定不正確，可能無法建立房間或同步棋步。

### 1.4 積分排位賽

- 對手 AI 的強度**依玩家目前段位自動調整**，玩家不能自行選擇難度。
- 登入並具備有效玩家資料後，才能保存個人排位紀錄；未登入也可以玩，但不會記錄積分，對手固定為青銅等級。
- 排位面板顯示目前積分、段位、升階進度條，以及「再幾分升到下一階」。
- 提供排行榜，設計目標為顯示前 10 名，並標示每位玩家的段位。
- 進入排位賽時，程式應先等待 Firebase 還原登入狀態，再判斷是否需要顯示登入視窗。
- 登入與註冊視窗應避免重複開啟；登入只需要電子郵件與密碼，使用者名稱在註冊時填寫。
- **按下「重來」會先跳出確認提示。** 若排位賽已超過 5 步，確認重來會依遊戲規則判定該局認輸；5 步以內則可確認後重新開始。
- 一局結束時，結果視窗會顯示這局加減多少分、技術加成明細，晉級時會有提示。

> 注意：前端鎖定模式或難度，不等於具備完整的伺服器端防作弊。若積分寫入權限允許使用者直接修改自己的分數，仍可能被惡意竄改。
> 正式競技環境應把結果驗證與積分計算移至可信任的伺服器端。

#### 段位表

起始積分為 1000。每個大段位分成 **I、II、III** 三小階。

| 段位 | 積分範圍 | 每小階 | 對手 AI | 勝／負基礎分 | 會掉段嗎 |
|---|---|---|---|---|---|
| 青銅 | 1000–1119 | 40 分 | 看 1 步，常失誤 | +30 / −5 | 不會 |
| 白銀 | 1120–1269 | 50 分 | 看 2 步，偶爾失誤 | +28 / −8 | 不會 |
| 黃金 | 1270–1449 | 60 分 | 看 3 步，很少失誤 | +26 / −10 | 不會 |
| 鑽石 | 1450–1689 | 80 分 | 看 4 步，不失誤 | +24 / −12 | 會 |
| 神話 | 1690–1989 | 100 分 | 思考 1 秒 | +22 / −14 | 會 |
| 傳奇 | 1990–2349 | 120 分 | 思考 2 秒 | +20 / −16 | 會 |
| 宗師 | 2350 以上 | — | 思考 3.5 秒 | +20 / −18 | 會 |

- 青銅～黃金設計為「容易上手」：對手較弱、贏一場加分多、輸了扣很少，而且**不會掉段**，打幾場就能升上去。
- 鑽石以上對手明顯變強，輸棋也會扣較多分。
- 和棋固定 +4 分，再加技術加成（最多 +6）。
- 原本已有積分的玩家，會依現有積分直接落在對應段位；舊的段位名稱（新手、進階、高手…）在玩家下一次打完排位後會自動換成新名稱。

#### 技術加成（最高 +12）

只有**獲勝**（或和棋，最多 +6）才會加分；**輸棋不計技術加成**。

| 項目 | 規則 |
|---|---|
| 吃子 | 每吃對方一子 +1，最多 +4 |
| 將軍 | 每將軍一次 +1，最多 +3 |
| 少失子 | 你被吃掉 ≤1 子 +3、≤3 子 +2、≤5 子 +1 |
| 速勝 | 雙方合計 40 手內獲勝 +2 |

- 排位面板會即時顯示「本局技術加成」目前累積了多少，並附有可展開的「技術加成怎麼算？」說明。
- 結果視窗會列出明細，例如：
  `排位 +38 分（基礎 +30，技術加成 +8：吃子 +3、將軍 +1、少失子 +3、速勝 +1）`

### 1.5 帳號系統

- 使用 Firebase Authentication 的電子郵件／密碼登入方式。
- 註冊時填寫電子郵件、密碼及使用者名稱。
- 登入時只需填電子郵件與密碼。
- 帳號登入狀態會由 Firebase 的登入狀態監聽器恢復及更新。
- 玩家資料與對戰紀錄依程式設計儲存在 Firebase Realtime Database。

### 1.6 管理員頁面

- 專案含有 `admin.html` 管理頁面。
- 管理功能會依程式設定的管理員 UID 判斷權限。
- 管理頁面顯示的在線資訊與管理項目，以目前版本的程式及 Firebase 規則為準。
- 不要只依靠前端隱藏按鈕保護管理功能；資料庫規則也必須驗證權限。

## 3. 網站如何運作

### 3.1 靜態網頁與 GitHub Pages

網站的 HTML、CSS 及 JavaScript 由瀏覽器載入。GitHub Pages 負責提供靜態檔案，不會自動執行伺服器端程式。

因此：

- 一般介面、棋盤繪製及部分遊戲邏輯在使用者的瀏覽器執行。
- AI 的計算會使用玩家裝置的 CPU。
- 連線房間、帳號、玩家資料及排行榜等雲端功能，需依賴 Firebase。
- 若 JavaScript 發生語法錯誤，相關程式可能無法啟動，導致棋盤空白或按鈕失效。

### 3.2 Firebase Authentication

登入流程通常如下：

1. 網頁載入 Firebase SDK 與專案設定。
2. Firebase 嘗試還原先前的登入狀態。
3. `onAuthStateChanged` 回報已登入的使用者，或確認目前沒有登入使用者。
4. 網站依登入狀態決定是否顯示登入視窗。
5. 登入成功後，再讀取玩家名稱、積分及其他帳號資料。

**重要：不能在 Firebase 尚未確認登入狀態時，就直接把 `currentUser === null` 當成未登入。**
網路延遲或初始化順序可能造成登入視窗重複跳出。應共用登入狀態初始化流程，並為登入視窗加上防重複機制。

### 3.3 Firebase Realtime Database

資料庫用於保存需要跨裝置同步的資料，例如房間、玩家資料、對戰紀錄及排行榜。
實際路徑與資料欄位由 `js/chess.js`、`js/home.js` 及 Firebase Database Rules 共同決定。

排位資料（`users/{uid}/ranked` 與 `rankedLeaderboard/{uid}`）包含：積分 `rating`、段位名稱 `tier`（例如「青銅 II」）、
本局加減分 `delta`、技術加成 `skillBonus`、勝敗和統計 `stats` 等欄位。

資料庫規則至少應遵守：

- 一般使用者只能讀寫自己有權存取的資料。
- 管理員操作必須在資料庫規則中驗證管理員權限。
- 不應因為前端隱藏功能，就假設資料已受到保護。
- 不要將密碼或服務帳號私鑰寫進前端程式。Firebase 網頁設定中的 API key 並非伺服器私鑰，但仍須搭配正確的 Authentication 與 Database Rules。

### 3.4 AI 如何運作

AI 的搜尋寫在 `js/xiangqi-ai.js`，由 `js/chess.js` 以 **Web Worker** 方式呼叫，所以 AI 思考時網頁不會卡住。

**搜尋技術：** 迭代加深、alpha-beta 剪枝、置換表、吃子排序、殺手與歷史啟發、晚走縮減、將軍延伸、靜態搜尋、重複局面判和。

**第一步開局：** AI 執黑第一步會從常見開局（屏風馬、順炮、列炮）隨機挑一個，每局不會完全一樣。

**強度如何調整：** `chess.js` 會把「強度設定」連同棋盤傳給 AI：

- **完整強度**：在指定的思考時間內越想越深（大師、神話以上段位）。
- **弱化模式**：固定深度、對每一步完整評分，再從「接近最佳」的走法裡隨機挑，並有一定機率故意走爛棋，但不會直接送車炮或被一步殺（新手、青銅～鑽石）。

**備援：** 若瀏覽器無法啟動 Worker，會自動退回舊版的簡易 AI，網站不會因此無法對弈。

**可調整的參數（都在 `js/chess.js`）：**

| 名稱 | 位置與用途 |
|---|---|
| `AI_TIME_PVE` | 單機「大師」的思考時間（毫秒），預設 1500 |
| `AI_NOVICE` | 單機「新手」的強度設定 |
| `RANK_TIERS` | 段位表：起始積分、每階分數、勝負基礎分、各段位的 AI 強度 |
| `SKILL_FAST_PLIES` | 「速勝」的手數門檻，預設 40 |

### 3.5 排位積分與公平性

前端可負責顯示積分、限制選單及呈現比賽結果，但前端程式可被使用者檢視或修改。
若需要可信任的競技排名，應由後端驗證棋步、結果與積分變化，再寫入排行榜。只靠瀏覽器端的判定無法完全防止作弊。

## 4. GitHub Pages 部署與更新

1. 下載專案 ZIP。
2. 解壓縮，確認檔案結構正確。
3. 將更新檔案上傳至 GitHub 儲存庫的對應路徑。**注意新增的 `js/xiangqi-ai.js` 必須放在 `js/` 資料夾內。**
4. 覆蓋同名的 HTML、CSS、JavaScript 檔案。
5. **保留原本的 `js/firebase-config.js`，不要刪除或覆蓋。**
6. 在 GitHub Pages 設定中確認發布分支及資料夾正確。
7. 等待 GitHub Pages 部署完成。
8. 開啟網站並使用 `Ctrl + F5` 強制重新整理，排除舊快取影響。

`chess.html` 載入 `chess.js` 與 `style.css` 時帶有版本參數（例如 `?v=20261109-skill-v48`）。
每次修改這兩個檔案後，記得一併更新版本參數，讓瀏覽器讀取新檔。

- [ ] 首頁能正常顯示。
- [ ] 棋盤能正常載入，沒有 JavaScript SyntaxError。
- [ ] 單機對戰可以走棋，AI 能回應；「新手」與「大師」兩種難度都能選。
- [ ] 開發者工具 Network 頁籤能成功載入 `xiangqi-ai.js`（狀態 200）。
- [ ] AI 思考時網頁不會卡住。
- [ ] 重來按鈕會先顯示確認提示。
- [ ] 排位面板顯示積分、段位與升階進度條。
- [ ] 排位賽的對手強度會依段位改變（青銅明顯較弱）。
- [ ] 排位賽中「本局技術加成」會隨著吃子、將軍即時更新。
- [ ] 結束一局後，結果視窗列出加減分與技術加成明細。
- [ ] 排位賽超過 5 步後，確認重來會依規則判負。

- [ ] 手機版排版正常。
- [ ] 管理員頁面權限符合預期。

## 5. 常見問題排查

### 棋盤空白

1. 開啟瀏覽器開發者工具（Windows 通常按 `F12`）。
2. 切到 **Console**。
3. 找第一個紅色錯誤，而不是只看最後一個訊息。
4. 記錄錯誤檔案、行號及版本參數。
5. 確認 GitHub 上的檔案已更新，並按 `Ctrl + F5`。
6. 檢查 JavaScript 語法及 Firebase SDK 是否成功載入。

`favicon.ico 404` 通常只表示網站圖示不存在，與棋盤程式的語法錯誤通常無直接關係。

### AI 一直不走棋，或走得很快很弱

- 確認 `js/xiangqi-ai.js` 已上傳到 `js/` 資料夾，且 Network 頁籤能成功載入（狀態 200）。
- 如果載入失敗，網站會退回舊版簡易 AI，看起來就是「AI 變弱了」。
- 確認 `chess.html` 載入的 `chess.js` 版本參數已更新，並按 `Ctrl + F5`。
- 在 Console 中查看是否有 Worker 相關的錯誤訊息。

### 登入視窗重複出現

- 確認所有頁面載入的是預期版本的 `js/chess.js` 與 `js/home.js`。
- 確認登入狀態只由共用的 Firebase Auth 狀態流程判定。
- 確認 Firebase 尚未完成狀態恢復時，程式不會立刻開啟登入視窗。
- 確認多個初始化函式共用同一個 Promise 或狀態鎖。
- 確認登入視窗已開啟時，不會再次建立另一個視窗。

### 積分沒有更新

- 確認 Firebase Authentication 顯示目前帳號已登入。
- 確認玩家 UID 與資料庫玩家資料路徑一致。
- 確認資料庫讀取與寫入權限正確。
- 區分「尚在載入」、「沒有資料」及「讀取失敗」，不要全部顯示成未登入。
- 未登入打排位賽不會記錄積分，這是正常行為。

### 段位或技術加成顯示不對

- 確認 `chess.html`、`css/style.css`、`js/chess.js` 三個檔案都已更新到同一版本。
- 排位面板的 `#ranked-skill`、`#ranked-tier` 等元素在 `chess.html`；若只更新 JS 而沒更新 HTML，這些顯示會缺失。

### 連線對戰無法使用

- 確認 Firebase 設定檔仍存在且內容正確。
- 確認 Realtime Database 已建立。
- 檢查 Database Rules 是否允許必要的讀寫操作。
- 查看 Console 與 Network 錯誤，不要為了方便而把資料庫規則全部開放。

## 7. 後續維護建議

- 每次更新後，記錄版本號、修改日期、修改檔案、修正內容及測試結果。
- 重大功能修改前，先保留上一個可正常運作的版本。
- 每次打包後檢查 ZIP 內容與 JavaScript 語法。
- 不要只以「語法檢查通過」代表功能已經完整測試；登入、Firebase 權限、連線對戰及積分寫入仍需實際測試。
- 將 Firebase 設定、資料庫規則與網站前端分開管理。
- 對正式排位賽，優先考慮後端驗證比賽結果，避免前端自行決定並寫入積分。
- 調整段位或技術加成數值時，只需修改 `chess.js` 中的 `RANK_TIERS`、`SKILL_FAST_PLIES` 與相關常數，並同步更新本文件的表格。
